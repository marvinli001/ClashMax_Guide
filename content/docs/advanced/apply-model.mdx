---
title: 变更生效模型
description: 按下应用之后发生什么：热重载、需要重启、下次启动，还是回滚。
---

同类客户端常见的一个问题是，一次规则修改和一次 DNS 修改在界面上长得一样，但一个是热生效、一个要重启、还有一个只是存进默认值等下次启动。一个什么都没做的修改和一个真正生效的修改看起来没有区别。

ClashMax 把这个边界写在界面上。按下保存之前，编辑器说明这次修改会做什么；保存之后，再确认一次实际发生了什么。两句话来自同一份计算逻辑。

## 四种结果

| 结果 | 含义 |
| --- | --- |
| 已应用到运行中的运行时 | Mihomo 重载了生成的配置，改动立即生效 |
| 已保存，需要重启 | 改动存下了，但没法折进当前进程 |
| 已保存，下次启动生效 | 当前没有承载用户流量的运行时 |
| 已回滚 | 运行时拒绝了这次改动，ClashMax 把它撤销了 |

<Callout type="warn">
「已回滚」值得单独留意。一个被静默撤销的修改在体验上等于工作丢失，所以它有独立的结果状态和明确的原因说明。
</Callout>

## 边界怎么算出来的

先看一个前提：当前运行时是否在承载用户流量。

```
运行时所有者 ∈ { user, tunnel, networkExtension }  且  不是预览运行时
```

不满足的话结果一律是「下次启动生效」。预览运行时被排除，是因为它只服务延迟测试，真正的运行时并没有起来。

满足的话按修改类型分：

| 修改类型 | 结果 |
| --- | --- |
| 规则、DNS、嗅探、原始 YAML、片段顺序、配置选项 | 热重载 |
| 入站端口、控制器端点 | NE 代理下需要重启，其余热重载 |
| NE 路由设置 | NE 代理下需要重启，其余下次启动生效 |

### 前六种为什么是热重载

它们全都被物化进那份生成的运行时 YAML，而每一种运行时所有者都支持就地重载它。

嗅探这一条实测确认过：对运行中的核心用一份关掉嗅探的配置做 `PUT /configs?force=true`，`/configs` 里的 `sniffing` 从 `true` 翻成了 `false`，不需要重启。

原始 YAML 片段归在热重载而不是重启，是因为 NE 代理在启动时固定的那两个键 `mixed-port` 和 `external-controller`，恰好是原始片段的[保留键](/docs/advanced/snippets#保留键)。片段不可能把它们从运行中的隧道底下抽走。

### NE 代理的两个例外

入站端口和控制器端点：NE 透明代理在启动时就捕获了当前的入站端口和控制端点，改了必须把隧道拆掉重建。

NE 路由设置（DNS 捕获、fake-ip、系统 DNS 覆盖）：只在隧道启动时读取，同理。

这是 Network Extension 的配置模型决定的，ClashMax 只能如实说明。

## 回滚发生在什么时候

生成的配置交给运行时之后，如果核心拒绝它（配置非法、DNS 组合不被接受、端口冲突等），ClashMax 撤销这次改动，并把运行时给出的原因原样告诉你，不会让你停在一个半应用的状态。

<Callout>
像 `respect-rules` 缺 `proxy-server-nameserver` 这类会让核心起不来的组合，在[生成阶段](/docs/advanced/runtime-config#为什么最后才校验-dns)就被拦住了。漏网的会在应用阶段被拒绝并回滚。
</Callout>

## 实践建议

编辑器底部那行字是这次操作的结果预告。它说「下次启动生效」，就现在重启核心，别等发现改动没生效再回来找原因。

大改之前先看路由页的「生效配置」，确认差异是你想要的再保存。规则类改动先在匹配模拟器里跑一遍，比应用之后再去连接页对答案快。

NE 代理下调端口，直接安排重启：改端口、重启运行时、验证。
