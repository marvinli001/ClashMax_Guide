---
title: 连接排查
description: 从一条连接反查规则、进程和链路，以及域名可见性为什么关键。
---

连接页显示核心当前处理的每一条连接，选中一条能看到进程、目标、命中的规则和完整链路。

## 看懂一条连接

| 字段 | 含义 |
| --- | --- |
| 进程 / App | 发起连接的程序 |
| 目标 | 域名或 IP |
| 规则 | 核心报告的命中规则 |
| 链路 | 从代理组到最终节点的完整路径 |
| 网络 | TCP / UDP |
| 上下行 | 该连接的流量 |

「按 App 分组」适合查某个 App 在连哪些地方。「历史」保留最近关闭的连接，排查那种一闪而过的请求时有用，因为它关得太快，实时列表抓不住。

单条连接可以关闭，也可以关闭全部连接。

## 域名可见性

每条连接的域名来源分三档，它决定了域名规则在结构上有没有可能生效：

| 来源 | 含义 |
| --- | --- |
| 客户端报告 | 客户端自己说了域名：HTTP `CONNECT`、SOCKS5 主机名，或者 fake-ip 被映射回域名 |
| 嗅探得到 | 客户端没给域名，嗅探器从流量里恢复出来的 |
| 没有域名 | 既没报告也没嗅探到 |

<Callout type="warn">
第三档要注意。一条直连 IP 打开的连接身上没有任何域名，为它写的 `DOMAIN`、`DOMAIN-SUFFIX`、`DOMAIN-KEYWORD`、`GEOSITE` 规则在结构上就不可能命中。规则没写错，只是根本没机会被评估。

解法是启用 DNS 或打开嗅探器，让域名重新出现，见 [DNS 与嗅探](/docs/advanced/dns-sniffer)。
</Callout>

「域名可见性」菜单可以按这三档筛选连接，一眼看出有多少流量在裸奔 IP。

## 为何命中此规则

选中连接后点「为何命中此规则」，会给出两份结论：

核心报告的结论，即 Mihomo 自己说命中了哪条规则、选了什么策略。以及本地模拟的结论，ClashMax 用当前规则列表在本地重跑一次匹配。

两者不一致，或者本地模拟得出「无匹配」，通常是因为连接身上缺少域名，或者有 provider 规则参与了匹配而本地看不到全部内容。

同一处还显示这条连接的域名可见性判定，能当场分清是规则写错了还是规则根本没被看到。

## 直接改规则

两个快捷动作把排查和修改接在一起。「为 xxx 添加规则…」直接为这个目标起草一条规则；「在『路由』页打开」把这条连接的上下文带进路由页，在片段库里正式写一条。

还有「为 xxx 解析 DNS」，当场看这个域名在当前 DNS 配置下解析成什么。

<Callout>
先在连接页确认域名可见性，再去写规则。顺序反了容易写出一条永远不会被命中的规则。
</Callout>
