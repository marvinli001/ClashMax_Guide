## 页面结构

**代理** 页有两种视图：**分栏** 是左边组、右边节点；**全部组** 是所有组平铺。节点可以按网格或列表呈现，也可以关掉节点详情让列表更紧凑。

排序有四档，默认那档最有用：

| 排序 | 含义 |
| --- | --- |
| **配置** | 保持配置里 `proxy-groups` 的顺序和组内成员顺序（默认） |
| **名称** | 按节点名 |
| **延迟** | 按最近一次测得的延迟 |
| **类型** | 按协议类型 |

节点多的时候用搜索框，或者用 **定位当前节点** 直接跳到正在用的那个。

## 切换节点

点节点即选中。两个附加行为值得知道：

- **切换后关闭旧连接**：打开后，换节点会顺手断掉已有连接，让它们用新节点重连。不打开的话，已建立的连接会继续走旧节点直到自己结束。想让切换立刻生效就打开它。
- **自动选择**的组（url-test / fallback 之类）会标成「自动选中」，你手动指定后就变成手动，直到你再改回去。

选择会被记住并写进运行时配置的 `now` 字段，重启后仍然是你选的那个——前提是这个节点在当前配置里还存在。

## 延迟测试

### 两种测法

**设置 → 运行时 → 延迟测试模式**：

- **Mihomo URL 延迟**（默认）：走 Mihomo 的代理延迟 API，真的经过节点发一次 HTTP 请求。测的是「这个节点能不能用、有多快」。
- **原生 Ping**：由 macOS 直接 ping 节点服务器地址。不经过核心，也不验证代理链路是否可用——服务器 ping 得通不代表节点能用。

日常判断节点可用性，用 Mihomo URL 那档。

### 统一延迟（Unified Delay）

打开后测两次握手，只报第二次，这样数字里不含首次连接的建链开销，节点之间更可比。

实现上两种模式不一样：Mihomo URL 模式把 `unified-delay` 写进运行时配置，由核心自己发第二次；原生 Ping 模式核心不参与，第二次探测由 ClashMax 自己发。

### 自定义测试 URL

可以给**单个组**设一个自定义延迟测试 URL。填错格式会回退到默认 URL 并给出提示。给不同用途的组配不同的目标（比如流媒体组测流媒体域名），比看一个统一的数字有意义得多。

### 批量测试

**测试当前组** 和 **测试全部组** 会跑一批。批量结果会汇总失败原因：超时、缺少端点、控制器不可用、已取消、其他。一批里少数几个超时是正常的；如果整批都报「控制器不可用」，问题在核心不在节点。

<Callout>
内置出站（`DIRECT`、`REJECT` 这些）没有可测的连接，测延迟对它们不适用。
</Callout>

### 核心没在跑也能测

想先挑好节点再启动？直接测就行——ClashMax 会自动起一个安静的**预览核心**专门跑测试，测完你选的节点会被记住。预览核心不接管任何流量，首页也会明确标出「预览运行时正在运行」。

<Callout type="warn">
预览运行时期间的配置修改一律算「下次启动生效」，因为真正的运行时并没有起来。
</Callout>

## Proxy Provider

如果配置用了 `proxy-providers`，**代理 Provider** 面板里可以：

- **全部更新** 或单独更新某个 provider
- 跑 **健康检查**，让核心重新评估 provider 里的节点

Provider 的节点数、更新时间、健康检查状态都在这里。**Provider 轻量分析** 会记录它们的历史表现，帮你判断某个 provider 是不是长期不稳。

规则类 provider 在[规则页](/docs/guide/rules-logs)管理，不在这里。
